### :fork_and_knife: This is a fork — which image should I use?

This repository ([avargaskun/wud](https://github.com/avargaskun/wud)) is a friendly fork of
[getwud/wud](https://github.com/getwud/wud). It was last synced with upstream on **2026-07-26** (just after
upstream `8.3.0`) and has grown its own features since. The image is published as
`ghcr.io/avargaskun/wud` and is a drop-in replacement: same env vars, same labels, same `/store` volume.

**The short version**

- Pick **this fork** if you let WUD *apply* updates (the `docker` / `dockercompose` triggers), drive it from
  scripts or an orchestrator through the API, watch containers on several hosts, or watch a lot of GHCR / LSCR
  images.
- Stick with **upstream** (`getwud/wud`) if you mostly use WUD for notifications, or if you want anything
  upstream shipped after our last sync — the Kubernetes, Nomad and Swarm watchers, update snooze and
  cool-down, the Home Assistant MQTT overhaul, the newer OIDC options, Docker Hardened Images, and so on.
  None of that is in this fork yet.

> [!WARNING]
> **Version numbers are not comparable.** Both projects publish `9.x` releases, but they are unrelated:
> this fork's versions are generated by release-please from its own history. `9.4.0` here is not upstream's
> `9.4.0`. See the fork's [CHANGELOG](CHANGELOG.md) for what each of our releases contains.

**What this fork adds**

- **Agent mode** — run a single WUD controller for your whole homelab. Each additional server only needs a
  lightweight WUD agent next to its Docker socket; the UI, the history, the notifications and the update
  triggers all live in one central place, so you get one dashboard for every host instead of one WUD per
  machine — and no Docker socket exposed over the network. ([docs](docs/configuration/agents/README.md))
- **Every update, not just the highest** — WUD reports the latest `major`, `minor`, `patch` and `digest`
  update separately (API `updates` field, notification templates, Prometheus labels). A `patch` threshold now
  really installs `1.2.4` when `2.0.0` also exists, instead of never firing.
  ([docs](docs/configuration/triggers/README.md))
- **Digest-only auto-updates** — a new `digest` threshold automatically picks up rebuilds of the tag you
  already run, while version bumps wait for a human. Works on semver tags too with
  `wud.watch.digest.semver=true`.
- **Lockstep batch updates** — a batch trigger API pulls *all* images first and only then swaps the
  containers, so stacks that must run matching versions (e.g. `immich` + `immich-machine-learning`) are never
  left half-updated for the length of a pull. You can also target a specific update kind with `bucket`.
  ([docs](docs/api/container.md))
- **Sidecar-aware updates** — `wud.postupdate.restart` bounces the containers that share an updated
  container's network namespace (the classic `gluetun` + `qbittorrent` breakage), once the new container is
  healthy. ([docs](docs/configuration/watchers/README.md))
- **Honest API answers** — trigger endpoints return what actually happened per container (`updated` /
  `failed`, plus dependents) and reject with a reason (`400` / `409`) instead of answering `200 {}` for an
  update that never took place.
- **Faster GHCR / LSCR checks** — tag listing resumes from where the previous cycle stopped instead of
  crawling every tag of every image, with an opt-in on-disk cache (`WUD_TAGCACHE_ENABLED`) so it survives
  restarts. ([docs](docs/configuration/storage/README.md))
- **Smaller things** — custom icon URLs for containers, cheaper handling of Docker create/destroy events,
  the container `auto` setting respected by API-triggered updates, and registry calls that retry a `429` /
  `502` / `503` / `504` (honouring `Retry-After`) instead of marking the container as errored for the cycle.

**Safer updates**

A good share of the fork's work is making the update triggers harder to hurt yourself with:

- A failed update **never leaves you without a container**: the original is renamed aside and rolled back
  instead of being removed first. This also fixes the `414` / `431` errors seen behind a Docker socket proxy.
- The replacement container picks up the **new image's** defaults (`ENV`, `CMD`, `ENTRYPOINT`, `HEALTHCHECK`,
  labels…) instead of carrying the old image's forever. Upstream has since fixed this too.
- The `dockercompose` trigger rewrites **only the updated service's** `image:` line — byte-for-byte otherwise —
  rather than every occurrence of the image string, and understands multi-file projects and
  mirror-prefixed pins.
- A typo in `wud.trigger.include` (`docker.update:pacth`) now **fails closed** with a warning instead of
  silently meaning "install everything, majors included".

**Before you switch**

A few of these are deliberate behavior changes, so skim the `:warning:` entries in the
[docs changelog](docs/changelog/README.md) first. The ones most likely to be noticed:

- Threshold-gated triggers start firing for lower-level updates that used to be masked, so containers that
  were silently never updating will start updating.
- The first watch cycle after switching produces one round of re-notification.
- Agents and controller must be upgraded together (controller first).

The fork also changes how update data is persisted in `/store`, so keep a copy of your `wud.json` if you
think you may want to go back to upstream. Bugs and ideas specific to the fork are
welcome in [our issue tracker](https://github.com/avargaskun/wud/issues); anything that also affects upstream
is best reported [there](https://github.com/getwud/wud/issues), and we aim to offer the fork's work upstream
over time.

### Agent Mode
WUD supports a distributed mode where "Agents" run on remote nodes to discover containers, and report back to a central "Controller".
See the [documentation](docs/configuration/agents/README.md) for details.
